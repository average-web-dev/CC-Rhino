# JS API Redesign (CC: Rhino)

Redesign of the `*API.java` surfaces for the Rhino/JS version — Node.js-oriented, **blocking by default**, with
callback variants and an engine-generated promise flavour of every module (`require('<module>/promises')`, see
[Async model](#async-model-promises)).

Source: analysis of `FSAPI`, `OSAPI`, `HTTPAPI`, `TermAPI`/`TermMethods`,
`RedstoneAPI`/`RedstoneMethods`, `PeripheralAPI`, `TurtleAPI`, `CommandAPI`, `PocketAPI`.

The new structure does **not** need to stay compatible with the old Lua API.

---

## Global design rules

| Topic | Lua/CC today | JS/Rhino new |
|---|---|---|
| **Multiple return values** | Lua can `return x, y` | JS cannot → **object** `{x, y}` or **array** `[x, y]`. Biggest incompatibility. |
| **Async** | Events/`pullEvent` | Thread-blocking by default; **error-first callback** `(err, result) => …` where Node has one; **Promises** via `require('<module>/promises')` |
| **Errors** | `nil, "msg"` pattern | Real errors → `throw new Error()`. "Expected" failure (e.g. `turtle.forward` into a wall) → result object |
| **Binary data** | string of bytes | `Buffer` / `Uint8Array` |
| **Sync suffix** | – | Blocking variant is named `…Sync` (Node convention), callback variant without suffix |

Chosen default conventions (overridable):
- Result of "can-fail" actions = `{success: boolean, reason?: string}`
- Coordinates/sizes = object instead of tuple

## `fs` — Node `fs` semantics (callback) + `fs.…Sync`

Follows Node.js semantics and, where the CC filesystem allows it, Node's signatures — typical Node `fs` code runs
unchanged. Every operation comes twice: blocking (`…Sync`, throws on error) and callback (`(err, res)`, delivered on
the next event-loop tick, after the call has returned; callbacks may use blocking APIs). Optional middle arguments
work as in Node (`fs.readFile(p, cb)` / `fs.readFile(p, 'utf8', cb)`). `require('fs/promises')` is generated by the
engine (#35) and mirrors Node's `fs/promises`: `readFile(path, options?)` returns a `Promise<string>` (it is
`readFileSync` returning a promise), likewise for every other pair; the CC extensions return promises too.

| Function | Parameters | Return (Sync) | Notes |
|---|---|---|---|
| `readFileSync` / `readFile` | `path, options?` (`encoding` or `{encoding?, flag?}`) | `string` | default encoding `utf8` (Node: Buffer); `latin1`/`binary`/`ascii` = one char per byte, `base64`, `hex`; `flag` ignored |
| `writeFileSync` / `writeFile` | `path, data, options?` (`encoding` or `{encoding?, flag?, mode?}`) | `void` | `data`: string or byte array; `flag` `w`/`a` + `x`/`+`; parent must exist (`ENOENT`) |
| `appendFileSync` / `appendFile` | same as `writeFile` | `void` | `flag` defaults to `a` |
| `readdirSync` / `readdir` | `path, options?` (`{withFileTypes?, recursive?}`) | `string[] \| Dirent[]` | `recursive` → relative paths |
| `mkdirSync` / `mkdir` | `path, options?` (`{recursive?}` or mode) | `string \| undefined` | `recursive` returns the first directory created |
| `rmSync` / `rm` | `path, {recursive?, force?}` | `void` | directory without `recursive` → `EISDIR` |
| `rmdirSync` / `rmdir` | `path, {recursive?}` | `void` | `ENOTDIR` / `ENOTEMPTY` |
| `unlinkSync` / `unlink` | `path` | `void` | directory → `EISDIR` |
| `renameSync` / `rename` | `src, dest` | `void` | replaces an existing file / empty dir at `dest` (Node) |
| `copyFileSync` / `copyFile` | `src, dest, mode?` | `void` | overwrites unless `COPYFILE_EXCL`; parent must exist |
| `cpSync` / `cp` | `src, dest, {recursive?, force? = true, errorOnExist?}` | `void` | merges directories, creates missing parents |
| `existsSync` / `exists` | `path` | `boolean` | `exists(path, cb(exists))` — Node's deprecated form, no `err` |
| `accessSync` / `access` | `path, mode? = F_OK` | `void` | `W_OK` on a read-only mount → `EROFS` |
| `statSync` / `stat`, `lstatSync` / `lstat` | `path, {throwIfNoEntry?}` | `Stats` | `lstat` = `stat` (no symlinks) |
| `realpathSync` / `realpath` | `path` | `string` | absolute, normalised; `ENOENT` if missing |
| `constants` | – | object | `F_OK R_OK W_OK X_OK COPYFILE_EXCL COPYFILE_FICLONE COPYFILE_FICLONE_FORCE`; `fs.F_OK` … also top-level |

### Errors

Errors are `Error`s with Node's properties and messages:
`ENOENT: no such file or directory, open '/missing.txt'`, `code` (`ENOENT`, `EEXIST`, `ENOTDIR`, `EISDIR`,
`ENOTEMPTY`, `EROFS` for read-only mounts, `EACCES`, `ENOSPC`, `EMFILE`, `EINVAL`, `EIO`), `errno` (negative Linux
value), `syscall`, `path` (absolute) and `dest` for two-path operations. Argument errors carry Node's `ERR_*` codes
(`ERR_INVALID_ARG_TYPE`, `ERR_INVALID_ARG_VALUE`, `ERR_UNKNOWN_ENCODING`). Implementation: `ScriptException`
can carry extra properties, which `JSMethodBridge` / `JSErrors` copy onto the JS `Error`.

## Async model (promises)

Decided in #35: **blocking stays the default**, promises are an explicit opt-in. Rhino has no `async`/`await`
syntax, but its `Promise` is real (and its jobs run on the event loop's microtask queue), so code written against
promises keeps working if Rhino ever gains `async`/`await`.

| Style | How | Use when |
|---|---|---|
| **Blocking** (default) | `require('turtle').dig()` returns the result; the calling thread waits, listeners and other threads keep running | Straight-line programs; concurrency through `parallel` green threads |
| **Promises** | `require('turtle/promises').dig()` returns `Promise<Result>` immediately | Starting several operations at once (`Promise.all`), composing with promise-based libraries |
| **Async functions** | TypeScript `async`/`await` (compiled to generators + `require('tslib').__awaiter`), or plain JS `require('async').run(function* () { var r = yield p; })` | Sequential code over promises |

- **`<module>/promises`** is generated by the engine for every native module (`turtle`, `fs`, `system`, `peripheral`,
  `events`, `parallel`, …): same function names, each returning a `Promise` of what the blocking form returns.
  Functions that never block return an already-settled promise; failures reject with the same `Error` the blocking
  form would throw (including properties like fs `code`). Node-style pairs collapse as in Node's `fs/promises`:
  `fooSync` + callback `foo` → promise-returning `foo` (`fsP.readFile(path)`). Objects returned through a
  `/promises` module get promise-returning methods too. Each has its own generated `.d.ts` (`TurtleAPIPromises`, …),
  and so does every object type (`HttpResponseHandlePromises`, `TransferredFilePromises`, …), which the promise
  modules' return types use. `parallel/promises`' `waitFor*` return a promise settled with the group.
- **`require('async')`** bridges both styles:
  - `run(genFn, ...args)` runs a generator function as an async function — `yield promise` awaits it (rejections are
    thrown at the `yield`). Returns a `Promise` of the return value. It is the same helper tsc uses.
  - `unwrap(p)` blocks the calling thread until `p` settles, then returns its value or throws its reason (non-promise
    values are returned unchanged). The blocking-code counterpart of `await`.
- **Blocking inside async code is an error**, never silently a promise: inside generators (and so `async`
  functions) and promise callbacks no continuation can be captured, so `turtle.dig()` throws
  `turtle.dig blocks and cannot be used inside async code — use require('turtle/promises') instead`. The same applies
  to callbacks run by native code (`Array.prototype.forEach`, a `Promise` executor, …), with a slightly different
  message. Functions that may block are rejected *before* running, so they have no effect: the engine captures the
  continuation before calling them (and drops it if they return immediately). "May block" is known for
  `@ScriptFunction`s (a `MethodResult` return or `mainThread = true`); functions returned as `IFunction` and methods
  of `IDynamicObject`s count as blocking unless they declare otherwise (`IFunction.nonYielding(fn)`,
  `IDynamicObject.isNonYielding(method)`), since the engine cannot know before calling them. `async.unwrap` and
  `parallel.waitFor*` always block.
- **Threads:** a promise reaction (`then`/`catch`/`finally`, `await`) belongs to the thread that registered it: it
  runs as that thread, and never once that thread has been stopped. An operation started through `/promises` belongs
  to the calling thread; if that thread is stopped, the operation is discarded and its promise rejects with
  `Error("Terminated")` — invisible to the stopped thread itself (its reactions don't run), but other threads awaiting
  the promise don't hang. Ctrl+T reaches a foreground thread blocked in `async.unwrap` like any other blocking call;
  pending `/promises` operations are not terminated directly, but end with their thread.
- **Unhandled rejections:** a promise rejected without a handler by the end of the microtask drain is reported, as in
  Node. If the thread that created it is still running, it fails with `Error("Unhandled promise rejection: <msg>")`
  (`cause` = the reason, `stack` = the reason's) — like Node ≥ 15, which exits the process: an async program that lost
  an error would otherwise continue half-dead. A foreground program thus ends, and bash prints the error. Rejections
  of the root thread (bios, shell) or of a thread that already returned are emitted as the `unhandled_rejection` event
  instead, which bash prints. Promises of a stopped thread never report. Attaching any handler (`then`, `catch`,
  `finally`, `await`, `Promise.all`, …) before the drain ends counts as handling it.
- **TypeScript:** the ROM compiles with `target: es2015` + `importHelpers`; `tslib` is a native module providing
  `__awaiter`, `__assign`, `__rest` and, for async generators / `for await`, `__await`, `__asyncGenerator`,
  `__asyncDelegator` and `__asyncValues` (`Symbol.asyncIterator` is polyfilled — Rhino lacks it). They are declared in
  `types/tslib.d.ts`, so code needing another helper fails to compile instead of at runtime. The build compiles with
  `src/build/compile-ts.mjs`, which parenthesizes every `yield` in tsc's output: Rhino rejects `f(yield x)` (from
  `f(await x)`) and parses `yield a, b` as `yield (a, b)`. TypeScript compiled elsewhere needs the same treatment, and
  plain-JS generators should parenthesize `yield` inside expressions. The Rhino authoring constraints still apply
  inside `async` functions (no `const` in loops, no spread).

```js
var turtleP = require('turtle/promises');
var async = require('async');

// Promise style: start two moves at once, continue when both are done.
Promise.all([turtleP.dig(), turtleP.digUp()]).then(function (r) { print(r[0].success && r[1].success); });

// Generator style, blocking the program until it finishes.
var mined = async.unwrap(async.run(function* () {
    var n = 0;
    while ((yield turtleP.dig()).success) n++;
    return n;
}));
```

```ts
import turtleP = require("turtle/promises");

async function mine(): Promise<number> {
    let n = 0;
    while ((await turtleP.dig()).success) n++;
    return n;
}
```

## Summary of the biggest changes

1. **`fs` split:** path logic → dedicated **`path` module**; `attributes`/`getSize`/`isDir` →
   `stat()` with a `Stats` object; `…Sync` + callback variant everywhere; `readFile`/`writeFile`
   convenience added.
2. **`os` broken apart** into **`process`** (computer control + in-game time), **`events`**
   (event bus, emitter preferred), and global **`setTimeout`/`setInterval`**. `date`,
   `dateString` and `utc`/`local` dropped (→ `Date`).
3. **`http`:** `request`/`get` as callback + `…Sync` blocking, `Response` object with
   `.json()/.text()/.buffer()`, `WebSocket` as an EventEmitter.
4. **Tuples → objects everywhere:** `getCursorPos`→`{x,y}`, `getBlockPosition`→`{x,y,z}`,
   turtle/pocket→`{success, reason}`.
5. **`term` coordinates 0-based** (JS-idiomatic, diverging from CC).

## Decisions

- **(a)** turtle/pocket result as **`{success, reason}`** ✅ (tuple `[ok, reason]` rejected)
- **(b)** `term` coordinates **0-based** ✅
- **(c)** path helpers in a **dedicated `path` module** ✅
- **(d)** computer control named **`process`** ✅
