# JS API Redesign (CC: Rhino)

Redesign of the `*API.java` surfaces for the Rhino/JS version — Node.js-oriented, **blocking by default**, with
callback variants and an engine-generated promise flavour of every module (`require('<module>/promises')`, see
[Async model](#async-model-promises)).

Source: analysis of `FSAPI`, `OSAPI`, `HTTPAPI`, `TermAPI`/`TermMethods`,
`RedstoneAPI`/`RedstoneMethods`, `PeripheralAPI`, `TurtleAPI`, `CommandAPI`, `PocketAPI`.

The new structure does **not** need to stay compatible with the old Lua API.

---

## Global design rules

| Topic | Lua/CC today | JS/Rhino new |
|---|---|---|
| **Multiple return values** | Lua can `return x, y` | JS cannot → **object** `{x, y}` or **array** `[x, y]`. Biggest incompatibility. |
| **Async** | Events/`pullEvent` | Thread-blocking by default; **error-first callback** `(err, result) => …` where Node has one; **Promises** via `require('<module>/promises')` |
| **Errors** | `nil, "msg"` pattern | Real errors → `throw new Error()`. "Expected" failure (e.g. `turtle.forward` into a wall) → result object |
| **Binary data** | string of bytes | `Buffer` / `Uint8Array` |
| **Sync suffix** | – | Blocking variant is named `…Sync` (Node convention), callback variant without suffix |

Chosen default conventions (overridable):
- Result of "can-fail" actions = `{success: boolean, reason?: string}`
- Coordinates/sizes = object instead of tuple

---

## `fs` — Node `fs` semantics (callback) + `fs.…Sync`

Follows Node.js semantics and, where the CC filesystem allows it, Node's signatures — typical Node `fs` code runs
unchanged. Every operation comes twice: blocking (`…Sync`, throws on error) and callback (`(err, res)`, delivered on
the next event-loop tick, after the call has returned; callbacks may use blocking APIs). Optional middle arguments
work as in Node (`fs.readFile(p, cb)` / `fs.readFile(p, 'utf8', cb)`). `require('fs/promises')` is generated by the
engine (#35) and mirrors Node's `fs/promises`: `readFile(path, options?)` returns a `Promise<string>` (it is
`readFileSync` returning a promise), likewise for every other pair; the CC extensions return promises too.

| Function | Parameters | Return (Sync) | Notes |
|---|---|---|---|
| `readFileSync` / `readFile` | `path, options?` (`encoding` or `{encoding?, flag?}`) | `string` | default encoding `utf8` (Node: Buffer); `latin1`/`binary`/`ascii` = one char per byte, `base64`, `hex`; `flag` ignored |
| `writeFileSync` / `writeFile` | `path, data, options?` (`encoding` or `{encoding?, flag?, mode?}`) | `void` | `data`: string or byte array; `flag` `w`/`a` + `x`/`+`; parent must exist (`ENOENT`) |
| `appendFileSync` / `appendFile` | same as `writeFile` | `void` | `flag` defaults to `a` |
| `readdirSync` / `readdir` | `path, options?` (`{withFileTypes?, recursive?}`) | `string[] \| Dirent[]` | `recursive` → relative paths |
| `mkdirSync` / `mkdir` | `path, options?` (`{recursive?}` or mode) | `string \| undefined` | `recursive` returns the first directory created |
| `rmSync` / `rm` | `path, {recursive?, force?}` | `void` | directory without `recursive` → `EISDIR` |
| `rmdirSync` / `rmdir` | `path, {recursive?}` | `void` | `ENOTDIR` / `ENOTEMPTY` |
| `unlinkSync` / `unlink` | `path` | `void` | directory → `EISDIR` |
| `renameSync` / `rename` | `src, dest` | `void` | replaces an existing file / empty dir at `dest` (Node) |
| `copyFileSync` / `copyFile` | `src, dest, mode?` | `void` | overwrites unless `COPYFILE_EXCL`; parent must exist |
| `cpSync` / `cp` | `src, dest, {recursive?, force? = true, errorOnExist?}` | `void` | merges directories, creates missing parents |
| `existsSync` / `exists` | `path` | `boolean` | `exists(path, cb(exists))` — Node's deprecated form, no `err` |
| `accessSync` / `access` | `path, mode? = F_OK` | `void` | `W_OK` on a read-only mount → `EROFS` |
| `statSync` / `stat`, `lstatSync` / `lstat` | `path, {throwIfNoEntry?}` | `Stats` | `lstat` = `stat` (no symlinks) |
| `realpathSync` / `realpath` | `path` | `string` | absolute, normalised; `ENOENT` if missing |
| `constants` | – | object | `F_OK R_OK W_OK X_OK COPYFILE_EXCL COPYFILE_FICLONE COPYFILE_FICLONE_FORCE`; `fs.F_OK` … also top-level |

**CC-specific extensions** (no Node equivalent, stay in `fs`):

|---|---|---|
| `getDrive` | `path` | `string \| null` |
| `getCapacity` | `path` | `number \| null` |
| `getFreeSpace` | `path` | `number \| "unlimited"` |

`mkdtemp`, `cp`'s `filter`, `Buffer`/`URL` paths, `Date` fields on `Stats`, the `fs.promises` property (use
`require('fs/promises')`).

### Errors

Errors are `Error`s with Node's properties and messages:
`ENOENT: no such file or directory, open '/missing.txt'`, `code` (`ENOENT`, `EEXIST`, `ENOTDIR`, `EISDIR`,
`ENOTEMPTY`, `EROFS` for read-only mounts, `EACCES`, `ENOSPC`, `EMFILE`, `EINVAL`, `EIO`), `errno` (negative Linux
value), `syscall`, `path` (absolute) and `dest` for two-path operations. Argument errors carry Node's `ERR_*` codes
(`ERR_INVALID_ARG_TYPE`, `ERR_INVALID_ARG_VALUE`, `ERR_UNKNOWN_ENCODING`). Implementation: `ScriptException`
can carry extra properties, which `JSMethodBridge` / `JSErrors` copy onto the JS `Error`.

## `events` — event bus (global singleton)

> **Note:** Node's `events` module exports the `EventEmitter` **class**. Here `events` is
> deliberately a **global singleton emitter** for the computer's events. There is deliberately no public
> `pullEvent`/`queueEvent`: blocking APIs wait for their own events internally, and a program reacts to events
> through listeners.

| Function | Parameters | Return | Kind |
|---|---|---|---|
| `on` | `event, cb` | `void` | EventEmitter (Phase 5) |
| `once` | `event, cb` | `void` | EventEmitter |
| `off` | `event, cb` | `void` | EventEmitter |
| `listenerCount` | `event` | `number` | EventEmitter |
| `emit` | `event, ...args` | `boolean` (had listeners) | EventEmitter, **synchronous** (Phase 13) |
| `queueMicrotask` / `setImmediate` / `clearImmediate` | `cb` / `cb` / `id` | `void` / `number` / `void` | event-loop scheduling |

**Native vs. custom events.** Native events come from the computer (input, timers, peripherals, `task_complete`,
…): they are declared as `@Event` records, typed by the generated `EventMap`, queued on the computer and delivered
on a later tick, where listeners may block. `events.emit` delivers a *script-defined* event synchronously, like
Node's `EventEmitter.emit`: the listeners run in registration order before `emit` returns, receive the arguments
unchanged, and `emit` returns whether there were any. Details:

- **Native names are reserved**: `emit('key')`, `emit('timer')`, `emit('task_complete')`, … throw an `Error` with
  `code: 'ERR_RESERVED_EVENT'`, so a program cannot fake input, timers or another program's task completion. All
  other names are free. Declare your events' arguments by augmenting `CustomEventMap`
  (`declare global { interface CustomEventMap { my_event: [count: number]; } }`), which types `emit`, `on`, `once`
  and `off`; emitting a native name is also a compile error.
- **Own listeners may block.** Listeners of the emitting thread or of a thread it belongs to (e.g. the program that
  started it with `parallel`) run as part of the caller and may block (`turtle.dig()`, `sleep`, …), which blocks the
  caller; `emit` returns once they have all finished. An error they throw is thrown from `emit` (remaining listeners
  are skipped, as in Node), and Ctrl+T reaches them like any blocking call of the caller. (`emit` is implemented in
  JS for this, so that a continuation can be captured through it.)
- **Listeners of other threads** (another program) run as their own thread and cannot block: blocking calls throw a
  clear error — defer such work with `setImmediate` or use a `/promises` module. An error there fails that program
  instead of the caller. Listeners of all threads run in registration order.
- `emit` called where nothing can block — inside an `Array.prototype.forEach` callback & co. (see #38), a generator
  or a promise callback — cannot let its listeners block either (same clear error).
- `require('events/promises').emit(...)` calls every listener without letting it block and returns an
  already-settled `Promise<boolean>`.
- Java code running inside the machine (a script method) can deliver an `@Event` record synchronously with
  `JSEventEmitter.current().fireNow(record)` (listeners cannot block there); everything else queues events on the
  computer.

**CC low-level timers/alarms** (they fire events; exposed by the `system` module):

| Function | Parameters | Return | Note |
|---|---|---|---|
| `startTimer` | `seconds` | `number` (id) | fires `timer` event |
| `cancelTimer` | `id` | `void` | |
| `setAlarm` | `time` | `number` (id) | fires `alarm` event (in-game time) |
| `cancelAlarm` | `id` | `void` | |

## Timers: `setTimeout` & co. (Node style, #45)

Like in Node these are **globals** (installed by the bios, `/rom/lib/internal/globals`), and also
`require('timers')` / `require('node:timers')` (the same functions). ROM TypeScript in `/rom/lib/timers` on top of a
native timer queue (`JSTimers` in the event loop, reached through the engine-internal `internal/loop` module).

| Function | Parameters | Return | Note |
|---|---|---|---|
| `setTimeout` | `cb, ms?, ...args` | `Timeout` | `cb.apply(timeout, args)` once after `ms` |
| `setInterval` | `cb, ms?, ...args` | `Timeout` | every `ms` until cleared |
| `clearTimeout` / `clearInterval` | `Timeout \| id` | `void` | also takes the numeric id (`Number(timeout)`) or it as a string; anything else is ignored |
| `setImmediate` | `cb, ...args` | `Immediate` | next tick, check phase (before timers) |
| `clearImmediate` | `Immediate` | `void` | |
| `queueMicrotask` | `cb` | `void` | global only, as in Node |

- **Ticks**: `ms` is rounded up to whole game ticks (1 tick = 50 ms), minimum one tick — `setTimeout(cb, 0)` runs on
  the next tick at the earliest, never synchronously. Invalid delays (NaN, negative, > 2³¹−1) become 1 ms, as in Node.
- **Order**: timers run in due-time order, timers due in the same tick in creation (re-arm) order; each callback is
  followed by its microtasks. Every pending timer has one CC timer; an interval re-arms after each run.
- **Threads**: like `events.on` listeners, a callback runs in the thread that created the timer, may block, and is
  discarded when that thread is stopped (Ctrl+T, `parallel` stop, the end of a shell job).
- **`Timeout`**: `ref()`/`unref()`/`hasRef()` (a ref'd pending timer keeps a shell job alive, see
  [job lifetime](#job-lifetime-46)), `refresh()` (restarts the countdown; re-arms a fired timeout), `close()`,
  `[Symbol.toPrimitive]()` → numeric id. `Immediate`: `ref`/`unref`/`hasRef` (a pending immediate always runs).
- **`require('timers/promises')`** (also `timers.promises`): `setTimeout(ms?, value?, { ref? })` and
  `setImmediate(value?, { ref? })` return promises; `setInterval(ms?, value?, { ref? })` is an async iterator for
  `for await` (leaving the loop clears the interval; values that fire while nobody waits are queued);
  `scheduler.wait(ms)` / `scheduler.yield()`. There is no `AbortController`, so `options.signal` is not supported.
- **No global `sleep`**: the CC way to block is `require('system').sleep(ticks)` (in ticks); without blocking,
  `await require('timers/promises').setTimeout(ms)` or `require('system/promises').sleep(ticks)`.
- `system.startTimer`/`cancelTimer` + the `timer` event stay as the low-level CC mechanism. The CC timers behind
  `setTimeout` fire `timer` events too (like `system.sleep`'s); listeners filter by their own ids.

### Job lifetime (#46)

bash runs each program as a job in its own thread. Like a Node process, the job stays alive after `main()` (or the
module's top-level code) returns while its thread tree has **ref'd pending work** (`EventLoop.isIdle`): a ref'd timer,
a blocked call or pending `/promises` operation, a queued immediate/microtask, a live child thread, or stdin it reads
(each `process.stdin` listener holds a keep-alive handle while stdin flows and is ref'd; `stdin.unref()` releases
it). Plain pending promises and `events.on` listeners do not keep it alive. If `main()` returns a promise
(`async main`, #44), a rejection is the program's error (exit code 1); a fulfilment value is not an exit code (use
`process.exitCode`). When nothing is left — or on `process.exit()` (from anywhere) — the job's thread is
**stopped**: leftover listeners, unref'd timers, promise reactions and background threads are discarded, so nothing
of the program runs or prints after the prompt. Ctrl+T reaches the wait like any blocking call. A program that
should outlive its job (a daemon) is not supported yet.

---|---|---|---|
| `setTimeout` | `cb, ms` | `number` (id) | preferred over `startTimer` |
| `setInterval` | `cb, ms` | `number` (id) | |
| `clearTimeout` | `id` | `void` | |
| `clearInterval` | `id` | `void` | |
| `sleep` | `seconds` | `void` | **blocking**, CC extension (deliberately absent in Node) |

## Node-style stdio: `process`, `console`, `util`, `readline` (#34)

There are no `print`/`write` globals. Like Node, the globals are `require` (engine), `process` and `console`
(installed by the bios); `require('process')` / `require('console')` return the same objects. All four modules are
TypeScript in the ROM (`/rom/lib`), ported from Node's JS sources, and resolve as "ROM core modules": before
`require.paths`, also with a `node:` prefix (`require('node:readline')`). Things a computer does not have (pid,
signals, memory usage, colour inspection, …) are absent rather than faked.

### `process`

| Member | Notes |
|---|---|
| `stdout`, `stderr` | `tty.WriteStream`-like: `write(chunk[, encoding][, cb])` (string or `Uint8Array`, Latin-1), `columns`/`rows`, `isTTY`, `cursorTo`/`moveCursor`/`clearLine`/`clearScreenDown`, `getWindowSize`, `hasColors`/`getColorDepth`. Text wraps at the right edge (VT pending-wrap) and scrolls; `\n \r \t \b` and ANSI sequences are interpreted: SGR colours map onto the 16 CC colours (ignored on monochrome terminals), plus CUU/CUD/CUF/CUB/CNL/CPL/CHA/CUP, ED, EL, SU/SD, save/restore, `?25h/l` (cursor blink). `stderr` writes in red. `'resize'` = the `term_resize` event (the computer's own terminal never resizes; a future window layer can emit it). |
| `stdin` | `tty.ReadStream`-like, fed by `char`/`key`/`paste`: `'data'`, `'keypress'` (`(sequence, key)` with `name`/`ctrl`/`meta`/`shift`), `'end'`; `setRawMode`, `isRaw`, `pause`/`resume`/`isPaused`, `readableFlowing`, `setEncoding` (always strings). **Cooked** (default): line discipline with echo, Backspace, Ctrl+U, Enter → `'data'` = line + `"\n"`, Ctrl+D on an empty line → `'end'` (the stream stays usable, like a terminal). **Raw**: each key as the VT sequence a terminal sends (`"\x1b[A"`, `"\r"`, `"\x7f"`, Ctrl+letter → control character). Nothing is read until the stream flows (a `'data'` listener or `resume()`); input arriving meanwhile is dropped. The cursor blinks while stdin flows. |
| `argv`, `argv0`, `execArgv` | `['bash', '/path/program.js', ...args]` while bash runs a program (`argv.slice(2)` = arguments) |
| `env` | live view of the `env` module (`PATH` mirrors `require.paths`); values are strings |
| `cwd()`, `chdir(dir)` | the shell's working directory; Node errors (`ENOENT`, `ENOTDIR`) |
| `exit([code])`, `exitCode` | ends the running program (throws a signal bash catches; also works from listeners and if caught, as the job is marked as exiting); outside a program (bios/shell) it shuts the computer down |
| `platform` | `'computercraft'` |
| `nextTick(fn, ...args)` | microtask |
| `hrtime([prev])`, `hrtime.bigint()`, `uptime()` | `Date.now()`-based (millisecond resolution); `uptime` = `system.clock()` |
| `emitWarning(msg[, type])` | prints `"Warning: msg"` to stderr |

**Thread ownership / foreground model.** The terminal driver's `char`/`key`/`paste` listeners are registered by the
bios (root thread) before anything else, so they run first for every event and translate it once.
`process.stdin.on(...)` registers *native* listeners in the calling thread, which pick up what the driver produced:
a program's stdin handlers therefore belong to the program — they may block, and Ctrl+T / stopping the program
discards them. bash runs every program as a **job**, like a child process: a fresh stdin (cooked, not flowing),
`process.argv` set, the cursor hidden until the program reads input, the working directory restored afterwards. After
`main()` returns the job keeps running while it reads stdin (stdin listeners and stdin not paused) — exactly when
Node would keep the process alive — so Node-style programs (`rl.on('line', …)`, then return) work; they end with
`rl.close()`, `process.stdin.pause()` or `process.exit()`. The job's leftover stdin listeners are closed when it ends,
and the shell's terminal state (raw mode, flowing) is restored. `main(args, cwd)` stays supported; it receives the
same values as `process.argv.slice(2)` / `process.cwd()`.

### `console`

Port of Node's `lib/internal/console/constructor.js`: a `Console` class (`new Console(stdout[, stderr][, ignoreErrors])`
or `new Console({ stdout, stderr, ignoreErrors, inspectOptions, groupIndentation })`, methods bound to the instance)
and the global console writing to `process.stdout`/`stderr`. `require('console')` returns the global console; its
`Console` property is the class.

`log`/`info`/`debug`/`dirxml` → stdout, `warn`/`error` → stderr (red), formatted with `util.format`; `dir(obj,
options)`; `trace(...)` ("Trace: …" + stack, stderr); `assert(value, ...msg)`; `count`/`countReset`;
`group`/`groupCollapsed`/`groupEnd` (indentation, default 2); `time`/`timeLog`/`timeEnd` (Node's time format);
`table(data[, properties])` (arrays, objects, `Map`, `Set`); `clear()`. Differences: tables use ASCII borders (`+-|`;
the terminal font has no box-drawing characters), inspected values break lines at the stream's width rather than 80
columns, no colour mode.

### `util`

`format` / `formatWithOptions` (`%s %d %i %f %j %o %O %c %%`, Node semantics incl. `%s` inspecting objects without
own `toString`, `-0`, `[Circular]`), `inspect` (port of `lib/internal/util/inspect.js`: `depth`, `showHidden`,
`maxArrayLength`, `maxStringLength`, `breakLength`, `compact` (incl. array grouping), `sorted`, `getters`,
`customInspect` + `inspect.custom`, `inspect.defaultOptions`; circular references as `<ref *1>` / `[Circular *1]`;
Maps, Sets, typed arrays, errors with stack, boxed primitives, null-prototype objects; `colors` is accepted and
ignored; promise states cannot be read on Rhino), `inherits`, `promisify` (+ `promisify.custom`),
`stripVTControlCharacters`, `styleText(format, text)` (ANSI codes, which stdout maps onto CC colours),
`isDeepStrictEqual`.

### `readline` and `readline/promises`

Port of Node's `lib/internal/readline/interface.js`. `createInterface({ input, output, prompt, completer, terminal,
history, historySize, removeHistoryDuplicates, crlfDelay, tabSize })` (or positional arguments); `Interface` with
`'line'`, `'close'`, `'pause'`, `'resume'`, `'history'`, `'SIGINT'` events, `prompt([preserveCursor])`,
`setPrompt`/`getPrompt`, `question`, `pause`/`resume`, `write(data[, key])`, `close`, `line`/`cursor`/`history`,
`getCursorPos()`, async iteration (`for await (const line of rl)`), and the module functions `cursorTo`,
`moveCursor`, `clearLine`, `clearScreenDown`, `emitKeypressEvents`.

- Terminal mode (default when `output.isTTY`): raw mode + keypress events, editing with Left/Right, Home/End
  (Ctrl+A/E), Backspace/Delete, Ctrl+B/F, word jumps (Ctrl+Left/Right, Meta+B/F), word deletion (Ctrl+W,
  Ctrl+Backspace, Meta+D), Ctrl+U/K, Ctrl+L, history (Up/Down, Ctrl+P/N, newest first, prefix search like Node,
  `historySize` default 30), tab completion via `completer` (sync, callback or promise; first Tab completes the common
  prefix, second Tab lists), Ctrl+C → `'SIGINT'` (or close without listeners), Ctrl+D on an empty line → close.
  Lines wrap over several rows. Non-terminal mode splits `'data'` into lines.
- **`question(query[, options][, callback])`**: with a callback as in Node; **without one it blocks** the calling
  thread and returns the answer (the blocking-by-default model). `require('readline/promises')` has the same
  `Interface` with a promise-returning `question`; closing the interface rejects a pending question with an
  `AbortError`. This module is hand-written like Node's: the engine generates `<module>/promises` only for native
  modules, ROM modules provide their promise flavour themselves where Node has one.
- Differences: a paused interface ignores input (process.stdin is shared with the shell, which pauses its own
  interface while a program runs); no kill ring/yank, undo or reverse search.

```js
// Blocking (default)
const rl = require('readline').createInterface({ input: process.stdin, output: process.stdout });
const name = rl.question('Name? ');
console.log(`Hi ${name}`);
rl.close();

// Node style: the program keeps running until the interface is closed
const repl = require('readline').createInterface({ input: process.stdin, output: process.stdout, prompt: 'calc> ' });
repl.on('line', (line) => { if (line === 'quit') return repl.close(); console.log(eval(line)); repl.prompt(); });
repl.prompt();
```

```ts
import readline from "readline/promises";
async function confirm(): Promise<boolean> {
    const rl = readline.createInterface({ input: process.stdin, output: process.stdout });
    const answer = await rl.question("Continue? ");
    rl.close();
    return answer === "y";
}
```

| `printer.getPageSize()` | `{width, height}` | `[width, height]` |
| `printer.newPage()` / `endPage()` | `Result` (`"No ink"`, `"No paper"`, `"Output tray is full"`) | `boolean` |

Detail tables (`ItemDetail`, `BlockDetail`, `EntityDetail`, …) stay Java `Map`s because other mods' detail
providers add fields; they are declared by hand in `projects/core/src/ts/types/details.d.ts` with an index
signature. Slot/tank maps stay `Record<number, …>` (sparse, keyed by 1-based slot). Events are declared as `@Event`
records (`CoreEvents`, `PeripheralEvents`) and form the generated `EventMap`; all core/common code queues events by
constructing these records (`queueEvent(Record)`), so the declared shape is the queued shape. A varargs record
(`computer_command(...args: string[])`) spreads its last component.

## Async model (promises)

Decided in #35: **blocking stays the default**, promises are an explicit opt-in. Rhino has no `async`/`await`
syntax, but its `Promise` is real (and its jobs run on the event loop's microtask queue), so code written against
promises keeps working if Rhino ever gains `async`/`await`.

| Style | How | Use when |
|---|---|---|
| **Blocking** (default) | `require('turtle').dig()` returns the result; the calling thread waits, listeners and other threads keep running | Straight-line programs; concurrency through `parallel` green threads |
| **Promises** | `require('turtle/promises').dig()` returns `Promise<Result>` immediately | Starting several operations at once (`Promise.all`), composing with promise-based libraries |
| **Async functions** | TypeScript `async`/`await` (compiled by Babel to generators driven by the engine's `babel-helpers`), or plain JS `require('async').run(function* () { var r = yield p; })` | Sequential code over promises |

- **`<module>/promises`** is generated by the engine for every native module (`turtle`, `fs`, `system`, `peripheral`,
  `events`, `parallel`, …): same function names, each returning a `Promise` of what the blocking form returns.
  Functions that never block return an already-settled promise; failures reject with the same `Error` the blocking
  form would throw (including properties like fs `code`). Node-style pairs collapse as in Node's `fs/promises`:
  `fooSync` + callback `foo` → promise-returning `foo` (`fsP.readFile(path)`). Objects returned through a
  `/promises` module get promise-returning methods too. Each has its own generated `.d.ts` (`TurtleAPIPromises`, …),
  and so does every object type (`HttpResponseHandlePromises`, `TransferredFilePromises`, …), which the promise
  modules' return types use. `parallel/promises`' `waitFor*` return a promise settled with the group.
- **`require('async')`** bridges both styles:
  - `run(genFn, ...args)` runs a generator function as an async function — `yield promise` awaits it (rejections are
    thrown at the `yield`). Returns a `Promise` of the return value. It is the same helper as tslib's `__awaiter`.
  - `unwrap(p)` blocks the calling thread until `p` settles, then returns its value or throws its reason (non-promise
    values are returned unchanged). The blocking-code counterpart of `await`.
- **Blocking inside async code is an error**, never silently a promise: inside generators (and so `async`
  functions) and promise callbacks no continuation can be captured, so `turtle.dig()` throws
  `turtle.dig blocks and cannot be used inside async code — use require('turtle/promises') instead`. The same applies
  to callbacks run by native code (`Array.prototype.forEach`, a `Promise` executor, …), with a slightly different
  message. Functions that may block are rejected *before* running, so they have no effect: the engine captures the
  continuation before calling them (and drops it if they return immediately). "May block" is known for
  `@ScriptFunction`s (a `MethodResult` return or `mainThread = true`); functions returned as `IFunction` and methods
  of `IDynamicObject`s count as blocking unless they declare otherwise (`IFunction.nonYielding(fn)`,
  `IDynamicObject.isNonYielding(method)`), since the engine cannot know before calling them. `async.unwrap` and
  `parallel.waitFor*` always block.
- **Threads:** a promise reaction (`then`/`catch`/`finally`, `await`) belongs to the thread that registered it: it
  runs as that thread, and never once that thread has been stopped. An operation started through `/promises` belongs
  to the calling thread; if that thread is stopped, the operation is discarded and its promise rejects with
  `Error("Terminated")` — invisible to the stopped thread itself (its reactions don't run), but other threads awaiting
  the promise don't hang. Ctrl+T reaches a foreground thread blocked in `async.unwrap` like any other blocking call;
  pending `/promises` operations are not terminated directly, but end with their thread.
- **Unhandled rejections:** a promise rejected without a handler by the end of the microtask drain is reported, as in
  Node. If the thread that created it is still running, it fails with `Error("Unhandled promise rejection: <msg>")`
  (`cause` = the reason, `stack` = the reason's) — like Node ≥ 15, which exits the process: an async program that lost
  an error would otherwise continue half-dead. A foreground program thus ends, and bash prints the error. Rejections
  of the root thread (bios, shell) or of a thread that already returned are emitted as the `unhandled_rejection` event
  instead, which bash prints. Promises of a stopped thread never report. Attaching any handler (`then`, `catch`,
  `finally`, `await`, `Promise.all`, …) before the drain ends counts as handling it.
- **TypeScript:** `src/build/compile-ts.mjs` type-checks with tsc and compiles with Babel (#49):
  `babel-preset-rhino` lowers `async` functions, async generators and `for await` to native generators driven by the
  `asyncToGenerator` / `wrapAsyncGenerator` / `asyncIterator` helpers of the engine's native `babel-helpers` module
  (`Symbol.asyncIterator` is polyfilled — Rhino lacks it), and parenthesizes every `yield`: Rhino rejects `f(yield x)`
  (from `f(await x)`) and parses `yield a, b` as `yield (a, b)`. `tslib` stays a native module for TypeScript compiled
  elsewhere (`importHelpers`): `__awaiter`, `__assign`, `__rest`, `__await`, `__asyncGenerator`, `__asyncDelegator`,
  `__asyncValues` and the `#private` helpers, declared in `types/tslib.d.ts`; such code needs its `yield`s
  parenthesized too, as do plain-JS generators.

```js
var turtleP = require('turtle/promises');
var async = require('async');

// Promise style: start two moves at once, continue when both are done.
Promise.all([turtleP.dig(), turtleP.digUp()]).then(function (r) { console.log(r[0].success && r[1].success); });

// Generator style, blocking the program until it finishes.
var mined = async.unwrap(async.run(function* () {
    var n = 0;
    while ((yield turtleP.dig()).success) n++;
    return n;
}));
```

```ts
import turtleP from "turtle/promises";

async function mine(): Promise<number> {
    let n = 0;
    while ((await turtleP.dig()).success) n++;
    return n;
}
```

## Summary of the biggest changes

1. **`fs` split:** path logic → dedicated **`path` module**; `attributes`/`getSize`/`isDir` →
   `stat()` with a `Stats` object; `…Sync` + callback variant everywhere; `readFile`/`writeFile`
   convenience added.
2. **`os` broken apart** into **`system`** (computer control + in-game time), **`events`**
   (event bus, emitter preferred), and global **`setTimeout`/`setInterval`**. `date`,
   `dateString` and `utc`/`local` dropped (→ `Date`).
3. **`http`:** `request`/`get` as callback + `…Sync` blocking, `Response` object with
   `.json()/.text()/.buffer()`, `WebSocket` as an EventEmitter.
4. **Tuples → objects everywhere:** `getCursorPos`→`{x,y}`, `getBlockPosition`→`{x,y,z}`,
   turtle/pocket→`{success, reason}`.
5. **`term` coordinates 0-based** (JS-idiomatic, diverging from CC).

## Decisions

- **(a)** turtle/pocket result as **`{success, reason}`** ✅ (tuple `[ok, reason]` rejected)
- **(b)** `term` coordinates **0-based** ✅
- **(c)** path helpers in a **dedicated `path` module** ✅
- **(d)** computer control named **`system`** ✅ (`process` is Node's process object, see #34)
- **(e)** no `print`/`write` globals: Node-style `console` / `process` globals and `util` / `readline` ROM modules ✅
  (#34)
